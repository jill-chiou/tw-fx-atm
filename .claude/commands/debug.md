# Systematic Debugging

當爬蟲失敗、資料異常、或任何 bug 出現時，必須依序完成以下四個階段，**不得跳過或合併**。

---

## 階段一：根因調查（Root Cause Investigation）

在任何修改之前：

1. 貼出**完整的錯誤訊息**（不是摘要，是原始 traceback）
2. 確認問題**可以穩定重現**——不能重現就不能修
3. 檢查**最近改了什麼**（`git diff`）
4. 在每個可能出問題的邊界加上 `print` 或 `logging`：
   - HTTP request 送出前：印出 URL、headers
   - response 回來後：印出 status code、前 500 字
   - 解析前：印出原始 HTML/JSON 結構

**禁止做的事**：
- 看到錯誤就說「我試試重跑」
- 不貼完整 traceback 就說「好像是網路問題」
- 同時修兩個以上的東西

---

## 階段二：模式分析（Pattern Analysis）

找出「可以動」和「不能動」的邊界：

- 其他爬蟲腳本在相同環境下是否能正常執行？
- 問題是特定銀行、特定縣市、特定幣別，還是全部都爆？
- 同樣的 API endpoint，用 curl 或 Postman 直接打能成功嗎？

---

## 階段三：假說與測試（Hypothesis & Testing）

1. 寫下一個**具體的假說**，例如：
   - 「永豐 API 對連續請求有速率限制，需要 sleep(1) 之間每次查詢」
   - 「兆豐需要 Referer header，缺少時回 403」
2. 做**最小的修改**驗證假說（只改一個變數）
3. 假說錯了，提出新假說，**不要繼續在錯的方向上疊加 code**

---

## 階段四：實作（Implementation）

1. 修正前，先寫一個能重現問題的測試（哪怕只是一個 `assert`）
2. 修正，確認測試通過
3. 如果修了三次以上還沒好：**停下來，問這個設計本身是不是有問題**

---

## 這個專案的常見根因速查

| 症狀 | 可能根因 | 驗證方法 |
|------|---------|---------|
| 爬蟲 connection error | IP 被暫時封鎖或 rate limit | sleep 後重試單一縣市 |
| 回傳空資料 | HTML 結構改版 | 印出 response.text 前 1000 字 |
| merge 後筆數少於預期 | bank_id 欄位 key 不吻合 | 印出兩份 JSON 的 key 樣本對照 |
| 地址比對失敗 | 正規化函數未涵蓋新格式 | 印出 normalize(原始) 的中間步驟 |
| TGOS 座標異常 | X/Y 欄位對調 | 確認 lng 在 119~122，lat 在 21~25 |
