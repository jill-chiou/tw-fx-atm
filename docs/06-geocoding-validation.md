# Step 05 — Geocoding Validation：抽樣驗證座標正確性

> 這份文件記錄如何確認 geocoding 產生的 Google Maps 座標是否真的對應到 ATM 的分行或裝設地點。

---

## 為什麼需要這一步？

Geocoding 會把文字地址轉成經緯度，但「有座標」不代表「座標正確」。

例如：
- 地址解析可能只找到同一條路，沒有精準到門牌。
- 大型場域（機場、醫院、校園、百貨）可能只落在建築或園區中心。
- 銀行分行、ATM 裝設點可能和 Google Maps 上的 POI 名稱不完全一致。

因此，除了程式自動檢查座標是否在台灣範圍內，還需要抽樣打開 Google Maps，用人眼確認點位是否合理。

---

## 為什麼選擇半自動驗證？

原本評估過用爬蟲或 Google Maps API 自動驗證座標是否對應到正確位置，但實作上有幾個問題：

1. **Google Maps 頁面不適合一般爬蟲**
   - Google Maps 是高度動態的前端頁面，內容由 JavaScript 載入。
   - DOM 結構複雜，容易因版面更新而失效。
   - 自動化操作可能遇到登入、語系、地區、反自動化限制等不穩定因素。

2. **Google Maps API 使用成本與設定成本較高**
   - 需要申請 API key。
   - 可能涉及額度、計費與服務條款限制。
   - 這個專案只需要驗證「座標是否落在合理位置附近」，不一定需要完整串接商業 API。

3. **判斷本身仍需要情境理解**
   - ATM 可能位於機場、醫院、校園、百貨或分行內部。
   - Google Maps 的座標有時會落在建物中心、場域入口或道路旁。
   - 這類情況很難用單純的文字比對或距離公式完全自動判定。

因此最後採用「半自動」方式：由程式負責抽樣、開啟地圖、記錄結果；由人負責判斷地圖點位是否合理。這樣可以兼顧效率、穩定性與判斷品質。

---

## 30 筆抽樣是否足夠？

本專案共有約 1,900 多筆 ATM 位置資料。抽樣 30 筆的目的不是要在統計上證明「全部資料 100% 正確」，而是作為資料品質檢查中的抽樣驗證。

### 可以支持的結論

如果 30 筆隨機抽樣全部通過，可以合理說明：

- 目前沒有在抽樣中發現明顯錯誤。
- geocoding 流程沒有出現大規模、系統性的偏移。
- 座標品質對地圖 MVP 來說具有初步可信度。
- 可作為開發階段的 smoke test 或 sanity check。

### 不能過度宣稱的結論

30 筆抽樣不能宣稱：

- 全部 1,900 多筆都正確。
- 整體錯誤率一定低於 1% 或 2%。
- 每一筆都精準到 ATM 機台所在位置。

### 用統計直覺理解

如果抽樣 30 筆且 0 筆錯誤，依照常見的「rule of three」估算，在 95% 信心水準下，整體錯誤率的上界大約是：

```text
3 / 30 = 10%
```

也就是說，30 筆全數通過大致可以支持「錯誤率不太可能高到 10% 以上」，但不足以證明錯誤率低於 5%、1% 這種更嚴格的標準。

如果之後要做更嚴謹的統計驗證，可以提高抽樣數：

| 目標 | 粗略需要的 0 錯誤抽樣數 |
|------|--------------------------|
| 95% 信心水準下，錯誤率低於 10% | 約 30 筆 |
| 95% 信心水準下，錯誤率低於 5% | 約 60 筆 |
| 95% 信心水準下，錯誤率低於 1% | 約 300 筆 |

因此，本專案目前採用 30 筆抽樣，是因為它適合用來確認 geocoding 流程沒有明顯系統性問題；若未來要把資料品質提升到更正式的審核標準，可以把抽樣數提高到 60 筆或 100 筆以上。

## 驗證資料來源

驗證前先執行：

```bash
python3 scripts/validate_and_fix_geocoding.py
```

這支腳本會：
1. 修正多重座標資料（例如 `lat` 或 `lng` 含 `;`）。
2. 檢查無座標資料。
3. 檢查座標是否超出台灣合理範圍。
4. 隨機抽樣 30 筆有座標資料，輸出 Google Maps 連結。

輸出檔案：

```text
data/processed/sample_validation.csv
```

欄位包含：

| 欄位 | 說明 |
|------|------|
| 銀行名稱 | ATM 所屬銀行 |
| 裝設地點 | 分行、商店、機場、醫院等裝設位置 |
| 地址 | 原始地址 |
| lat / lng | geocoding 產生的座標 |
| Google Maps 連結 | 用座標開啟的地圖連結 |

## 人工判定標準

判定原則：**只要該分行或 ATM 裝設地點位在 Google Maps 開啟的座標點附近，就算通過。**

這個專案的目標是讓使用者能在地圖上找到可用的外幣 ATM，因此不要求座標精準到建築物內部的 ATM 機台位置。只要使用者依照地圖能到達正確分行、商店或場域附近，就符合使用情境。

### OK：可接受的情況

- 點位落在同一棟建築物。
- 點位落在同一個銀行分行附近。
- 點位在同一個路口或同一側街廓，和地址明顯相符。
- ATM 位於大型場域內，例如機場、醫院、校園、百貨、賣場，點位落在該場域內或主要入口附近。
- Google Maps 上顯示的地名、門牌、道路位置與 CSV 的地址或裝設地點一致。

### NG：不通過的情況

- 點位落在不同路段、不同街區，明顯離地址太遠。
- 點位跑到不同鄉鎮市區或不同城市。
- 同名分行但位置在另一個地點。
- 座標顯示在海上、山區、河流、空地等明顯不可能的位置。
- Google Maps 開啟後的位置和地址完全無法對應。

### Skip：暫不判定的情況

- Google Maps 資訊不足，無法判斷。
- 地址本身不完整或疑似 PDF 解析錯誤。
- 裝設地點在管制區或建築內部，外部地圖無法確認，但也看不出明顯錯誤。

## 半自動驗證流程

為了避免手動打開 CSV、逐一複製連結，可以使用互動式腳本：

```bash
python3 scripts/review_sample_maps.py
```

腳本會逐筆：
1. 在終端機顯示銀行名稱、裝設地點、地址、座標。
2. 自動開啟該筆 Google Maps 連結。
3. 等待人工輸入判定。
4. 即時把結果寫入 review CSV。

操作方式：

| 輸入 | 意義 |
|------|------|
| Enter / `o` | OK，座標通過 |
| `n` | NG，座標不正確，可輸入備註 |
| `s` | skip，暫時跳過 |
| `b` | 回到上一筆 |
| `q` | 離開 |

輸出檔案：

```text
data/processed/sample_validation_review.csv
```

輸出欄位會保留原本資料，並新增：

| 欄位 | 說明 |
|------|------|
| review_status | `ok` / `ng` / `skip` |
| review_note | 人工備註 |
| reviewed_at | 驗證時間 |

## 腳本使用的技巧

`review_sample_maps.py` 的設計重點不是完全取代人工判斷，而是把重複、容易出錯的操作交給程式處理，讓人工只專注在「地圖點位是否合理」這件事。

### 1. 使用標準函式庫完成瀏覽器自動開啟

```python
import webbrowser

webbrowser.open(row["Google Maps 連結"])
```

`webbrowser` 是 Python 內建模組，不需要額外安裝套件。它會用系統預設瀏覽器開啟 Google Maps 連結，因此這支腳本可以在不同電腦上直接執行。

這裡沒有使用 Selenium 或 Playwright，原因是本流程不需要操作 Google Maps 頁面內部元素，只需要把正確連結依序打開給人工確認。使用標準函式庫可以降低環境設定成本，也避免 Google Maps 動態頁面或反爬蟲機制造成不穩定。

### 2. 用 CSV DictReader 保留欄位語意

```python
with open(path, encoding="utf-8-sig", newline="") as f:
    return list(csv.DictReader(f))
```

`csv.DictReader` 會把每一列轉成 dictionary，之後可以直接用欄位名稱讀資料，例如：

```python
row["銀行名稱"]
row["地址"]
row["Google Maps 連結"]
```

這比用欄位位置（例如 `row[0]`, `row[1]`）更安全，因為 CSV 欄位順序改變時，程式比較不容易讀錯資料。

`encoding="utf-8-sig"` 則是為了處理 Excel 常見的 UTF-8 BOM，避免第一個欄位名稱變成帶有隱藏字元的 `\ufeff銀行名稱`。

### 3. 互動式命令列輸入，降低人工紀錄成本

```python
answer = input("判定？").strip().lower()
```

腳本每開一筆地圖，就等待使用者輸入判定結果。這種做法把人工驗證流程固定成幾個簡單指令：

| 指令 | 意義 |
|------|------|
| Enter / `o` | 通過 |
| `n` | 不通過 |
| `s` | 跳過 |
| `b` | 回上一筆 |
| `q` | 離開 |

人工不需要另外複製貼上資料，也不需要手動維護另一份 Excel，只要看地圖後輸入一個字元即可。

### 4. 即時寫入結果，避免中途關閉造成資料遺失

```python
save_reviews(rows, reviews)
```

每完成一筆判定，腳本就會立刻把目前結果寫入 `sample_validation_review.csv`。這樣即使中途關閉終端機、瀏覽器當掉，或只想分批驗證，也不會遺失已完成的紀錄。

這個設計比全部驗證完才一次寫檔更安全，特別適合需要人工逐筆檢查的工作。

### 5. 使用 row_key 對應既有 review，支援中斷後續跑

```python
def row_key(row: dict[str, str]) -> str:
    return "|".join(
        [
            row.get("銀行名稱", ""),
            row.get("裝設地點", ""),
            row.get("地址", ""),
            row.get("lat", ""),
            row.get("lng", ""),
        ]
    )
```

腳本用銀行名稱、裝設地點、地址與座標組成一個簡單的 key。這個 key 用來判斷某一筆資料之前是否已經驗證過。

這樣做的好處是：
- 可以讀取既有的 `sample_validation_review.csv`。
- 已經驗證過的資料不會被誤認成新資料。
- 腳本可以從第一筆尚未驗證的資料繼續。

### 6. 自動尋找第一筆尚未驗證資料

```python
def first_unreviewed_index(rows, reviews):
    for index, row in enumerate(rows):
        reviewed = reviews.get(row_key(row), {})
        if not reviewed.get("review_status"):
            return index
    return 0
```

如果前一次只驗證到第 12 筆就離開，下一次重新執行腳本時，程式會自動從第 13 筆開始，不需要人工記住上次做到哪裡。

### 7. 保留人工備註與驗證時間

```python
"review_note": note,
"reviewed_at": time.strftime("%Y-%m-%d %H:%M:%S"),
```

除了 `ok` / `ng` / `skip`，腳本也會記錄備註與時間。這讓驗證結果不只是「通過或不通過」，而是可以回頭追溯：
- 誰在什麼時間點做了驗證。
- NG 的原因是什麼。
- Skip 的資料是否需要之後再補查。
