# UI 與幣別資料研究計畫

> 目標：把目前 MVP 從「能用的地圖」推進成「手機上真的好查、好看、可維護的外幣 ATM 工具」。

> 目前狀態（2026-05-09）：UI 第二版已落地到 `index.html`，包含圓形 marker、浮動搜尋列、bottom sheet、銀行篩選面板與文字搜尋。資料來源盤點已整理到 `docs/07-bank-data-inventory.md`。下一步從「研究」轉為「UI polish QA + 新光銀行幣別爬蟲 POC」。

## 1. UI 方向

**狀態：已實作，剩下 polish QA。**

### 地圖點位

目前的 pin 比較接近傳統地圖圖釘。下一版可以改成更圓潤、比較像產品 UI 的點位：

- 預設狀態：圓形 badge，外圈白色描邊，內圈銀行色。
- 選取狀態：放大一點，增加陰影，popup 或底部資訊面板同步打開。
- 密集狀態：之後可加 marker cluster，cluster 用柔和圓角數字點。
- 銀行辨識：短期先用顏色，長期可以加銀行代號或簡短 initials，避免 18 種顏色太難記。

可參考方向：

- GeoLeaf：地圖、篩選、popup、detail panel、data table 的整體組合。
- BootLeaf / nakeyMap：搜尋框、側欄列表、地圖範圍內列表同步。
- MapLibre/modern map UI：全螢幕地圖上疊浮動控制，而不是把工具列固定成傳統表單。

### 篩選與搜尋

現在的銀行篩選是橫向 chip，手機上要一直右滑，不適合銀行數量一多的情境。建議改成混合式：

- 第一層：搜尋框，使用者可以直接輸入銀行、地點、地址、縣市。
- 第二層：常用快速篩選，例如「附近」、「台北」、「美元」、「日圓」（幣別資料完成後）。
- 第三層：進階篩選用 bottom sheet 或 dropdown panel，裡面放銀行多選、幣別多選、縣市。

這樣不用在主畫面塞滿所有銀行，也符合手機查找行為：先打字，找不到再開篩選。

### 版面

建議採用「地圖全螢幕 + 浮動搜尋列 + 底部結果面板」：

- 頂部：搜尋列、定位按鈕、篩選按鈕。
- 地圖：佔滿主要畫面。
- 底部：附近 ATM / 搜尋結果列表，可收合、半展開、全展開。
- Popup：保留精簡資訊，詳細資訊交給底部面板，避免手機 popup 太擠。

視覺語言可以偏「乾淨、柔和、金融工具感」：

- 背景用接近白的冷灰，不用大面積藍色。
- 主色可保留可信任感的藍綠色，但降低飽和。
- ATM 點位用較溫暖的 accent，讓地圖上可見。
- 卡片/面板圓角 8px 以內，點位可更圓潤。

## 3. 幣別資料盤點策略

**狀態：已完成第一輪盤點，詳見 `docs/07-bank-data-inventory.md`。下一步是新光銀行 POC。**

目前主資料來源是財金資訊 PDF，優點是完整，缺點是只提供位置，不提供每台 ATM 的幣別明細。下一步要補 USD / JPY / HKD / EUR / CNY 等幣別，應該先盤點各銀行資料格式。

### 先盤點，再決定爬法

每家銀行建立一份 inventory：

| 欄位 | 說明 |
|------|------|
| bank_code | 銀行代號 |
| bank_name | 銀行名稱 |
| source_url | 外幣 ATM 查詢頁或 PDF |
| source_type | HTML / JSON API / PDF / embedded data |
| has_currency | 是否有每台 ATM 幣別 |
| fields | 地址、分行、幣別、營業時間等 |
| crawl_method | requests / Playwright / pdfplumber / manual |
| join_key | 如何跟現有資料合併：地址、裝設地點、銀行代號 |
| risk | 反爬、格式易變、資料不完整 |

### PDF vs 網頁

PDF 不一定比較難，重點看格式：

- 表格型 PDF：適合 `pdfplumber`，可重現、版本化，通常穩。
- 掃描 PDF：需要 OCR，不建議優先。
- 靜態 HTML 表格：最容易，用 requests + parser。
- 動態網站：先看 network 有沒有 JSON API；有 API 就打 API，沒有再用 Playwright。
- 地圖型查詢頁：通常資料藏在 API 或 JS 變數，要從 network 抓。

### 建議先做的銀行

先挑 3 到 5 家資料量大、頁面相對可解析的銀行做 proof of concept：

- 玉山：已有外幣 ATM 查詢頁，頁面有搜尋、定位、列表、地圖檢視。
- 台灣銀行、兆豐、台新、中信：外幣需求常見，值得優先盤點。
- 若某家只有 PDF 且表格穩定，就優先納入，因為維護成本可能比動態網站低。

## 4. 搜尋實作細節

**狀態：已實作到 `index.html`。本機快速 QA：搜尋「高雄三民」可命中 27 筆，銀行篩選面板可開啟，390x844 手機 viewport 下主要控制項可見，未發現 console error。**

### 比對策略

前端搜尋對每筆 ATM 把「銀行名稱 + 裝設地點 + 地址」串成一段文字，再對查詢字串做比對。

**問題：** `String.includes()` 純子字串比對無法處理台灣地址的行政單位字（市、縣、區、鄉、鎮），例如搜尋「高雄三民」找不到「高雄市三民區」，因為中間插了「市」字。

**解法：** 查詢字串長度 ≥ 4 時，加一層「每 2 字一組 AND 比對」的 fallback：

```
"高雄三民" → chunks: ["高雄", "三民"]
→ 每個 chunk 都出現在目標文字 → 命中
```

| 查詢 | chunks | 目標 | 結果 |
|------|--------|------|------|
| 高雄三民 | [高雄, 三民] | 高雄市三民區中華三路 | ✓ |
| 兆豐台北 | [兆豐, 台北] | 兆豐銀行台北分行 | ✓ |
| 信義 | — | 信義路五段 | ✓（純子字串） |
| 玉山 | — | 玉山銀行 | ✓（純子字串） |

**比對流程（`matchQuery` function）：**
1. 試完整子字串 → 命中就返回
2. 查詢長度 ≥ 4 → 切成 2 字一組，全組都出現就命中
3. 否則不命中

**已知限制：**
- 查詢字數為奇數時，最後一組可能只有 1 個字（容忍度略高）
- 不支援拼音或英文地址的模糊比對
- 未來若資料量大到影響效能，可改用 Fuse.js 或 lunr.js 等前端搜尋套件

### 搜尋技術背景：一般做法有哪些？

做一個搜尋功能，通常從幾個維度來選：**比對方式**、**索引方式**、**中文處理**。

#### 比對方式

| 方式 | 原理 | 優點 | 缺點 |
|------|------|------|------|
| 子字串 `includes()` | 查詢字串整段出現在目標裡 | 最簡單、精準 | 不容許任何字符在中間 |
| 詞組 AND | 把查詢切成幾個詞，每個詞都要出現 | 容許詞間有其他字 | 需要知道怎麼切詞 |
| 模糊搜尋（Edit Distance） | 允許幾個字打錯，計算「改幾個字才能一樣」 | 打錯字還是找得到 | 中文不適合（字形差異大，改一個字意義完全不同） |
| 全文索引（Inverted Index） | 事先把每個詞對應到哪些文件，查詢時直接查表 | 非常快，支援 AND/OR/NOT | 需要建索引、佔記憶體 |

**模糊搜尋（Fuzzy Search）補充：** 這是英文搜尋很常見的技術，例如使用者打 `"Taiepi"` 可以找到 `"Taipei"`。計算方式是 Levenshtein Distance（最少要增、刪、改幾個字母才能一樣）。Fuse.js 就是前端常見的模糊搜尋套件，支援設定容許幾個字元的誤差。但中文不適合：中文「高雄」和「高熊」只差一個字，卻是完全不同的概念，容許誤差反而會出現奇怪的結果。

#### 索引方式

一般應用層級的搜尋分兩種：

**即時掃描（Linear Scan）：** 每次搜尋都逐一看每筆資料，判斷有沒有符合。這個專案目前就是這種。約 1,900 筆資料，每次搜尋大概幾毫秒，完全足夠。

**預建索引（Inverted Index）：** 事先把每個詞對應到文件清單。例如「高雄」→ [ATM_id_3, ATM_id_7, ATM_id_102]。查詢時直接查表取聯集或交集，不用掃描全部資料。Elasticsearch、Algolia、MeiliSearch 都是這種架構。幾百萬筆才需要考慮。

#### 中文特有問題：斷詞

英文以空格天然分隔，`"New York City"` 很容易切成三個詞。中文沒有分隔符，`"高雄市三民區中華三路"` 要怎麼切取決於斷詞演算法（如 jieba、CKIP）。

斷詞後就能建詞組索引，讓「高雄」「三民區」「中華三路」各自成為可搜尋的詞。但斷詞套件通常要在 server 端跑（Python/Node.js），純前端 JS 環境不容易使用。

**前端常見的替代方案是 N-gram：** 不管語意，直接把文字切成固定長度的片段（通常 2 字），然後建索引。

```
"高雄市三民區" → bigrams: [高雄, 雄市, 市三, 三民, 民區]
```

搜尋「高雄三民」→ 取其 bigrams [高雄, 雄三, 三民] → 三個都要有命中文件。

這個專案的 2 字分組 AND 是 N-gram 的簡化版：不用重疊（步進 2 而非 1），也不預建索引，只在查詢時即時算。優點是不需要任何套件、資料量小時速度夠快。

#### 為什麼這個專案選現在的做法

| 條件 | 決定 |
|------|------|
| 資料量約 1,900 筆 | 不需要預建索引，即時掃描夠快 |
| 純靜態前端，無 server | 不能用 Python 斷詞，也不想引入大型 JS 套件 |
| 查詢對象是台灣地址 | 主要障礙是行政單位字（市縣區），2 字分組能解決 |
| 不需要容許打錯字 | 不用模糊搜尋 |

如果未來資料量增加到數萬筆，或需要支援打錯字仍能找到，可以考慮引入 **Fuse.js**（純前端，支援模糊比對 + 多欄位權重）或改用後端搜尋服務。

## 5. UI 決策紀錄

### 按鈕標籤 + Empty state 行動化（第二版）

**問題：** 頂部右側兩個 icon-only 按鈕（定位、篩選）沒有文字標籤，使用者需要猜測功能。底部 empty state 只有一段提示文字，不能直接點擊。

**使用者實際流程：** 開啟 app → 定位 → 篩選有帳戶的銀行 → 看最近幾家。這個流程的兩個關鍵動作都藏在 icon-only 按鈕裡，不夠明顯。

**為什麼不做流程引導（onboarding）：**
流程引導本身要考慮「只顯示一次」（localStorage）、使用者跳過後的狀態、不同裝置的行為，做不好反而造成干擾。且目前還沒有足夠的使用者數據確認問題存在，不適合押注在大功能上。

**改動（最小改動原則）：**
1. 按鈕加文字標籤：`定位`、`篩選`，圖示保留輔助識別
2. Empty state 改成兩個並排的行動按鈕：「找附近 ATM」直接觸發定位，「選擇銀行」直接開篩選面板

**原則：** 先做能直接降低認知負擔的最小改動，觀察反應，再決定是否需要更大的引導機制。
